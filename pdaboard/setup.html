PA PDA Operations Dashboard

Local setup walkthrough

How to stand up the PDA Board on a work computer: get the code, pull the SharePoint file tree, point it at the right folders, drop in the Chart A / Table A workbooks, and build the board. Each step says what you feed it and the format.

Handling note. This page and the tool's code are safe to share. The actual PDA inputs are not: Chart A / Table A workbooks, the SharePoint query.xlsx export, and everything the board builds (out/) contain live damage figures, applicant details, and staff names. Keep those on the work machine only — they are git-ignored and never leave it. Unofficial working tool; not a declaration determination.

0 Prerequisites

Get Python and the one library the parser needs.
  • Python 3.9+ — check with python --version (on Windows, py --version also works).
  • openpyxl — the only hard dependency (reads the .xlsx workbooks). Install: 
    pip install openpyxl
  • Optional, only if you ever rebuild county geometry with build_dim_county.py: a US counties GeoJSON saved as counties_us.json (Census 20m). The board ships with the six Region 5 states' dims already built, so you normally don't need this.

No internet is required to run the board — it's fully offline. Network is only used by build_history.py (refreshing the prior-FEMA-history snapshot from OpenFEMA).

1 Get the code onto the work computer

Clone the repo, then work inside the pdaboard/ folder.
# clone (or: download the repo ZIP from GitHub and unzip)
git clone https://github.com/calebpaulsmith/DisasterParameters.git
cd DisasterParameters/pdaboard
What's in the repo vs what isn't. The public repo carries only the code — parsers, pipeline, the board template, county reference data, this page. It does not carry any PDA data (PDAExamples/, out/, tests, the Excel builder workbook). You supply the PDA inputs locally, per the steps below.

2 Pull the SharePoint file tree (the "tree export")

Snapshot the PDA library so the board knows each Chart A's validation stage and its live SharePoint link.

The board figures out how far each county's Chart A has progressed from where the file sits in SharePoint. To read that, it needs a snapshot of the library's file tree:

  1. Open the PDA's SharePoint document library in the browser.
  2. Switch to a flat / "All items" view (so every file in every subfolder is listed, not just the top level).
  3. Export to Excel (the ribbon button). SharePoint hands you a query.iqy web-query that opens in Excel and fills a table of every file with its folder path, modified date, author, and URL.
  4. In Excel, Save As → query.xlsx and drop it into your PDA folder (next to the Chart A's).
  5. Keep the query.iqy too and drop it in the same folder. One library-wide export/.iqy (rooted at Ongoing PDA's) works for every PDA — the build narrows it to this one by name, or you name it with sp_folder in the manifest / the board's PDA folder picker. The export's path column is server-relative — the .iqy is the only file that carries the SharePoint host and this PDA's root folder, which is what turns every file row and county row into a working link.
Format: query.iqy — a few lines of text carrying the site URL and RootFolder=. Parsed by: sp_filetree.parse_iqy() at build time (any *.iqy in the drop, or --iqy <file>) and by the board itself: Admin → SharePoint links → Load query.iqy… re-points every link in an already-built board (on a finished board the Admin surface is the small gear in the header). Without it the board still builds — links are simply inert, flagged NO_SHAREPOINT_LINKS in Data health.
Format: query.xlsx — one row per file, columns for name, folder path, modified, modified-by, and item URL (whatever your SharePoint export produces; sp_filetree.py matches on the path + filename). Parsed by: sp_filetree.py. Optional for a live PDA — a "complete" PDA can be built from just the Table A + Chart A's with no query.xlsx at all (stage falls back to the folders on disk).

The export is a point-in-time snapshot — re-export whenever you want the board's stage badges and file links to reflect the latest SharePoint state (see step 7).

3 Identify the right folders (the stage model)

A Chart A's stage is which folder it lives in. Drop files keeping their folder structure.

The validation workflow is encoded by folder. When you copy files into the local drop folder, preserve these subfolders so the board reads the right stage:

StageShown asSharePoint / drop folder
1 · WorkingNot yet submittedDamage Data/Counties/<County>/ (field copies)
2 · For PDA Lead ReviewFor PDA Lead ReviewChart A's/1. For PDA Lead Review/ (+ loose Chart A's at the root)
3 · Ready for Table AReady for Table AChart A's/2. Ready for Table A/ (a local Validated/ ranks the same)
4 · Entered in Table AEntered in Table A.../2. Ready for Table A/Entered in Table A/

Stage 0 = a county in scope with no Chart A anywhere. Only counties through Lead Review (stage ≥ 3) count toward the rollups and threshold math; earlier stages show as pending (visible via the header's "Pending $" admin toggle).

What the board needs: the Chart A's copied in with their pipeline subfolders intact, plus (optionally) the county working folders. Underscore folders are ignored — anything in a _-prefixed folder (e.g. _17-19 import, _ref, _code) is never parsed as part of the PDA.

4 Chart A & Table A workbooks

Table A carries the dollars and indicators; Chart A's add comments, applicant types, and inspectors.

Table A (the master — required)

The statewide/county per-capita indicators, state population, and every county's validated Cat A–G dollars come from the Table A workbook. One Table A per PDA. Two template generations are both read automatically (by cell label, never fixed positions):

  • v2 (RVAR-era): has an RVAR sheet; per-county table on Summary.
  • legacy (SummaryPage-era): no RVAR sheet; per-county table on SummaryPage, indicators on PCI Indicator.

Chart A's (per county — optional enrichment)

Each county's Chart A adds what a Table A can't: validation comments (rich text preserved), applicant type, and the FEMA inspector. Dollars are always taken from the Table A, so a Chart A is never required for a county to appear — it just enriches the drill-down.

Format: .xlsx FEMA Chart A / Table A templates (either generation). Trust rule: county identity comes from the workbook cell, not the filename (filenames lie — a "Blank Chart A" file can hold real data); every total is recomputed from Cat A–G and reconciled against the workbook's own cells, mismatches flagged. Parsed by: chart_a_parser.py.

5 Write the PDA manifest

A tiny per-PDA config: identity, the events, and your SharePoint root (for deep links).

Each PDA has a manifest.json. Indicators are never put here — they're read from the Table A. The manifest is just identity + the SharePoint base URL that turns file rows into working deep links. 5b Or skip steps 3–5: the build wizard (point it at your folder)

Download the PDA's folder from SharePoint — the whole thing (or "Final Products"), or just a folder you piled the Chart A's into — and point the wizard at it. No hand-arranged folders, no hand-written manifest.
# from inside pdaboard/ — one folder in, one board out
python wizard.py

Press Enter at the folder question and a Windows folder-picker opens — browse to the downloaded folder (pasting a path, or passing it on the command line, still works). The wizard also offers an optional prior-FEMA-history refresh (default No; needs internet — any failure is skipped, the existing snapshot stays).

The wizard reads the folder where it is — nothing is moved, staged, or copied — and classifies what it finds by name (content-sniffing any workbook whose name says neither):

  • "…Table A…" .xlsx — the Table A master. The wizard also reads the state and incident month out of it, so the identity prompts are just Enter-Enter. If the folder carries several Table A's (e.g. a full one and a "Counties That Met Threshold Only" cut), the wizard lists them and asks which one is the master — the choice is pinned in the manifest.
  • "…Chart A…" .xlsx — Chart A's. Each one's stage is the folder it sits in ("Entered in Table A", "2. Ready for Table A", "1. For PDA Lead Review" — anywhere in the path), so a downloaded folder keeps its stages. Loose charts on a complete build are final anyway; on a live build the wizard asks one stage for all of them.
  • query.xlsx and query*.iqy — the SharePoint export + its web query (step 2), picked up wherever they sit.

It prints what it found, asks the identity questions (defaults pre-filled from the Table A), writes one small _manifest.json beside your files (underscore-prefixed = never parsed as PDA data), runs the pipeline, and prints the path to the finished out_*/board.html. Dropped more files into the folder later? Re-run the same command — or the printed pipeline.py line — and the board rebuilds.

When to use which: the wizard is the fast path for any folder you can download or assemble; steps 3–5 (hand-arranged drop + manifest) remain the way to control every detail by hand — the wizard is doing exactly that for you under the hood.

6 Build the board

One command joins everything and writes a single self-contained HTML file.
# from inside pdaboard/, pointing at your drop folder
python pipeline.py                          # uses ./manifest.json + ./PDAExamples (default drop)
# or an explicit drop + manifest + output dir:
python pipeline.py --drop "C:\path\to\PDA drop" --manifest manifest.json --out out

# then open it (fully offline — file:// works, or serve it):
python -m http.server 8137 --directory out  # http://localhost:8137/board.html

The result is out/board.html — one file, no network calls, ~400 KB. It's emailable and opens on any machine. After a template-only edit, re-render instantly without re-parsing: python rehtml.py.

Prior-history card (bottom of each county drill-down) reads data/history_<state>.json, a static OpenFEMA snapshot shipped in the repo. To refresh it to today's date: python build_history.py (needs network), then rebuild.

7 Refresh during a live PDA

Repeat as the assessment progresses — each run is a snapshot; changes show as "Movers."
  1. SharePoint library → flat view → Export to Excel → save over query.xlsx (step 2).
  2. Copy the current Chart A's (+ the Table A) into the drop folder (step 3–4).
  3. python pipeline.py → refresh the browser. Each run appends a snapshot (skipped if nothing changed); movement since the last run appears under "Movers."
